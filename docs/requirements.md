# 项目需求文档：AccountKeeper 本地记账软件

## 1. 项目概述
使用 Python 编写一个带图形界面（GUI）的本地记账小工具。该工具需操作简单、界面友好，通过图形化交互完成记账、查账、统计等功能，数据必须持久化保存在本地。

## 2. 技术限制
- **语言**：Python 3.13。
- **依赖**：使用 `customtkinter` 库作为 GUI 基础框架，使用 `Pillow` (PIL) 库处理图片，使用 `matplotlib` 库处理图表，使用 `platformdirs` 库管理用户数据目录。其他尽量只使用 Python 标准库（如 `sqlite3`, `csv`, `datetime`, `pathlib`, `json`, `random`）。
- **存储**：使用本地 SQLite 数据库文件 `account.db` 存储数据，数据库位置固定在用户数据目录下、路径不可自定义。用户上次导出 CSV 的目录记在 `settings.json` 中，仅用作下次导出时的起始目录。
- **配置**：设置 `settings.json`，仅用于保存「上次导出路径」（`last_export_dir`）。程序启动时必须先读取该配置；配置缺失、损坏、非法或目录不可用时，自动回退默认目录（`DATA_DIR`），**不弹窗、不崩溃**。
- **规范**：代码必须符合 PEP 8 规范，命名清晰，关键逻辑必须配有中文注释。

## 3. 核心功能需求

### 3.1 数据持久化（SQLite 数据库）
- **数据目录**：使用 `platformdirs.user_data_dir("AccountKeeper", "SpringU26325")` 获取用户数据目录（Windows 下通常为 `C:\Users\用户名\AppData\Local\AccountKeeper`），并在启动时自动创建该目录。
- `account.db` 固定存放在该用户数据目录下（路径不可自定义），**绝对不允许**放在临时解压目录或程序安装目录。
- 启动时自动连接 `account.db`。如果数据库或表不存在，自动创建。
- 数据库包含 `accounts` 主表（ID、日期、金额、`category`、备注）和 `record_tags(record_id, tag)` 标签关联表；一条记录可关联 0 个或多个标签。`category` 列保留但停止写入、降为 legacy 只读。
- SQLite 使用 `PRAGMA user_version` 跟踪 schema 版本；启动时将旧数据库迁移至版本 2。存在待补标签记录时，迁移前将数据库备份为 `account.db.bak`。设计理由详见 §3.14.2。

- 每次修改记录（添加、删除）后，必须**立刻提交事务（commit）**，防止数据丢失。
- 推荐使用 `contextmanager` 封装数据库连接，确保连接稳定关闭。

### 3.2 添加记录 (Add)
- 提示用户输入：日期（默认今天，格式 `YYYY-MM-DD`）、金额、标签和备注（可选）。
- **输入区采用标题行 + 三行字段的布局**：
  - 标题行：左侧「添加记录」标题，右侧为紧凑操作区（「支出/收入」切换按钮与「添加」按钮成组，间距 12px，整体靠右，右侧留卡片内边距 16px）；两个按钮等高 36px、垂直居中
  - 第一行：日期字段（输入框 + ▼ 按钮）、金额字段
  - 第二行：标签区（标签 chips、输入框和 ▼ 按钮）
  - 第三行：备注字段
  - 三行字段按同一套列网格对齐；标签区和备注字段横跨输入列
  - 日期、金额、标签区和备注字段随窗口宽度自适应，标签区可随标签数量换行增高
  - 图标型控件（▼ 按钮、支出/收入切换、添加按钮）保持固定宽度
  - 任何窗口宽度下，所有字段保持完整可见、不重叠、不留大片空白
  - 宽度约定：日期字段与标签区的 ▼ 按钮各为 36px，支出/收入切换为 120px，添加按钮为 96px，两者高度均为 36px、间距 12px；按钮字体统一为 11、圆角统一为 9；日期框与金额框按 15 : 25 的比例分配输入列宽度，标签区和备注字段横跨输入列；卡片左右内边距 16px；字段区与标题行垂直间距约 8-10px，三行字段之间垂直间距约 10px；字段标签位于输入框左侧。标题行最右侧的「添加」按钮与备注框右边缘对齐。
  - 视觉层级：「添加」为主操作，蓝底白字；「支出/收入」切换为状态指示，浅灰底、浅蓝选中态、深色文字，无灰色外框。
- 日期字段采用「输入框 + ▼ 图标按钮」的组合。输入框允许手动输入 `YYYY-MM-DD`；点击 ▼ 按钮弹出日历选择器，选中日期后回填到输入框（详见 3.12）。
- 标签区由已选标签 chips、输入框和 ▼ 按钮组成；输入后按回车将标签加入当前记录，点击 chip 上的 × 只移除当前记录的该标签。▼ 打开多选列表，点选项目切换选中态，点击「完成」后将选中标签整体回填。候选来自 `tags.json` 的单一有序列表，不随支出 / 收入切换；手输标签只影响当前记录，加入常用列表需在弹窗中点「+ 保存」。首次初始化由 `tag_prefs.ensure_tags_initialized(history)` 处理：优先保留已有 `tags.json`，否则迁移有效的 `categories.json` 两段；旧文件不可用时才以预置标签和数据库历史初始化。

- **【支出 / 收入】切换按钮**（使用 `CTkSegmentedButton`，位于标题行中间偏左）默认选中【支出】，它只决定金额的正负号。
- 用户始终输入正数。系统在保存时，根据选中的状态进行转换：
  - 如果选择【支出】，自动将金额转为**负数**。
  - 如果选择【收入】，保持**正数**。
- 金额不能为 0。如果用户输入非数字（包括NaN），需弹出错误提示框（目前错误提示框的非数字和日期格式不对耦合，以后要分开）。
- 每条记录自动生成唯一的 ID（自增主键）。

### 3.3 查看记录 (View)
- 使用 `customtkinter` 搭配 `ttk.Treeview` 控件以表格形式展示所有记录。
- 表格需包含滚动条，列头包括：ID、日期、金额、标签、备注；多个标签在单元格内用顿号连接，0 个标签显示 `—`。
- 表头与各列单元格文字统一水平居中，包括备注列。

- （需求变更）不显示「收: x | 支: y | 记录数: n」的汇总标签：该标签已删除，工具栏只保留搜索框和工具按钮，汇总改由【月度统计】与【查看图表】提供。

### 3.4 统计分析 (Stats)
- 点击按钮弹出月历让用户点选月份，不再手输 `YYYY-MM`：4 列 × 3 行共 12 个「n 月」格子，标题显示当前年、点 ◀ / ▶ 翻年，底部左键由「今日」变为「本月」；复用现有的 `ask_month` 方法，返回值恒为严格的 `YYYY-MM`。
  （月份弹窗不传锚点、固定屏幕居中显示，原因与后续计划见 §3.12 约束）
- 统计该月总支出和总收入；总额按记录各计一次，不因记录标签数量而膨胀。
- 支出明细按标签分别计入：多标签记录在每个标签下计入整笔金额，0 标签记录计入 `未分类`。
- 明细之和可能大于总支出；有支出明细时，在列表后显示说明：「一条记录有多个标签时会分别计入各项，故各项之和可能大于当期总额；未分类表示没有打标签的记录。」

- 如果没有支出记录，给出友好的文字提示。

### 3.5 删除记录 (Delete)
- 选中表格中的某条记录，点击【删除选中记录】按钮。
- 弹出确认对话框，询问“确认删除该记录吗？”（使用自定义 `CTkToplevel` 弹窗，不用原生 `messagebox`；理由：原生弹窗无法定制配色、无法标红危险按钮，Windows 上的原生弹窗还会自动显示 Y/N 快捷键字母，与中文界面不搭）。
- 如果 ID 不存在，提示用户“找不到该记录”。

### 3.5.1 编辑记录 (Edit)（临时插入，与3.5没有关系，主要目的是防止打乱排序）
- **触发方式**：双击表格中的某一行记录。（暂时不够user-friendly，新用户容易不知道怎么编辑，以后加提示）
- **弹窗内容**：弹出一个编辑对话框，包含日期、金额、标签区（chips + 输入框 + ▼）和备注，**必须预填当前记录的旧值**。日期字段采用「输入框 + ▼ 图标按钮」的组合，点击 ▼ 弹出日历，选中后回填；标签区的 ▼ 打开多选列表，点选后切换选中态，点击「完成」后整体回填标签。
- **数据校验**：日期格式必须为 `YYYY-MM-DD`，金额必须为非零有效数字；标签允许为空。

- **保存逻辑**：
  - 在 `AccountStore` 类中设置 `update` 方法，接收 `record_id`、日期、金额、标签元组和备注，更新 `accounts` 记录并替换该记录的 `record_tags` 关联。
  - **必须使用 `contextmanager` 的连接，并在事务成功后 `commit`**。
  - 更新成功后，调用 `refresh_records()` 刷新表格。
- **取消操作**：用户点击“取消”或按 `ESC` 键，关闭弹窗，不修改任何数据。
- **关闭收尾**：编辑、删除确认和标签弹窗关闭时清理本窗及子控件所属定时/idle任务，保留其他窗口任务；子标签窗构建期间收到父编辑窗关闭请求，完成初始化后立即兑现，避免对已销毁控件继续绑定或恢复焦点。关闭可重复调用，父窗退出时同样收尾。
- **数据一致性**：编辑过程中，不得修改该记录的 ID（ID 是数据库主键，永远不变）。

### 3.6 导出为 CSV (Export)
- 在界面上添加一个【导出为CSV】按钮。
- 点击后弹出月历，让用户点选想要导出的月份（返回值恒为严格的 `YYYY-MM`），复用现有的 `ask_month` 方法。
- 如果该月没有记录，弹出提示“该月没有记录，无法导出”，流程结束。
- **选择保存路径（核心改动）**：
  - 用户输入月份并确认后，调用 `tkinter.filedialog.asksaveasfilename()` 弹出 Windows 原生“另存为”对话框。
  - 参数设置：
    - `defaultextension=".csv"`
    - `initialfile=f"account_export_{month}.csv"`
    - `initialdir=str(last_export_dir)`，即上次导出用过的目录；没有记录或记录已失效时用 `DATA_DIR`（见 3.11）。
    - `filetypes=[("CSV 文件", "*.csv"), ("所有文件", "*.*")]`
  - 如果用户点击“取消”（返回空字符串），直接终止导出，不报错、不弹窗，也不写配置。
  - 导出成功后，将用户**实际选择的目录**写回 `settings.json` 的 `last_export_dir`（见 3.11）；写回失败只在控制台警告，不影响已完成的导出。
- **写入逻辑（在 `store.py`）**：
  - `export_month_csv` 方法签名为 `def export_month_csv(self, month: str, save_path: Path) -> Path:`。
  - 直接写入用户选定的 `save_path`，写入成功后返回该路径。
  - 如遇写入异常（权限、磁盘满等），向上抛出，由 UI 层捕获。

- **CSV 列结构**：表头由 `CSV_FIELDS` 提供，标签列名为 `tags`；一条记录的多个标签在同一单元格内用 `|` 连接（`日用|家庭`），0 个标签写空串。使用 `|` 而非逗号，可避免 CSV 引号转义给文本分列或按逗号拆分带来额外处理（详见 §3.14.4）。

- 导出成功后，弹出提示框告知用户文件的具体保存路径。

### 3.7 应用内装饰：动态蜗牛 (Interactive Snail)
- **图片处理要求**：使用 `image/snail_blue_anti.png` 的透明深蓝加粗蜗牛，保留原造型，去除网格、坐标轴和文字。逻辑显示尺寸保持在 40x40 像素左右；高分辨率源图交给 CTkImage 按 DPI 缩放，不先缩成小图再放大。候选素材必须具有透明背景和可见线条，缺失或损坏时跳过；没有可用素材时只跳过蜗牛装饰，不影响记账功能。
- **位置要求**：蜗牛作为独立小组件，直接悬浮在主窗口（`self`）的最顶层，用 `lift()` 确保不被其他控件遮挡。入场、动画与传送统一使用窗口内物理像素，垂直位置固定为 y=15 物理像素；CTk 仅负责图片尺寸缩放，不缓存或再次缩放蜗牛的位置。
- **启停与清理**：运行中重复 `start()` 保留当前控件、位置、气泡及唯一动画链；`stop()` 可重复调用，取消动画、气泡关闭、布局和焦点任务，精确移除自身事件绑定，释放蜗牛及气泡。父窗口、标题或蜗牛被外部销毁时自动收尾；父窗口与标题仍存活时允许重新启动。已停止或控件销毁后不得再续期暂停心跳。
- **窗口事件**：仅主窗口本身的 Map 触发入场，恢复显示不重置已入场位置；焦点事件合并到空闲阶段，按实际焦点所属顶层决定暂停。同一主窗口内切换输入控件不暂停，切到其他窗口或无焦点时暂停；回到主窗口后只有气泡已关闭才恢复。事件绑定追加安装，清理不得覆盖或移除其他订阅者。
- **循环卷轴动画效果**：
  - **起点**：蜗牛从窗口顶部的右侧边缘出发（x = 窗口宽度）。
  - **向左爬行**：每次让 x 坐标减去 2~3 像素。
  - **传送门逻辑 1（标题文字边缘）**：当蜗牛爬行到 `AccountKeeper` 标题文字的右侧边缘时，瞬间传送到标题文字的左侧边缘，继续向左爬行（不能从标题文字上穿过去）。
  - **传送门逻辑 2（屏幕边缘）**：当蜗牛爬出 GUI 窗口的最左侧边缘（x < 0）时，瞬间传送到窗口最右侧（x = 窗口宽度），重新开始向左爬行。
- **点击交互（对话泡泡）**： 
  - **使用主窗口内的局部 `tk.Canvas` 来绘制气泡**（独立窗口的延迟很高）
  - **底层实现**：软件仅面向 Windows；`_show_speech_bubble` 创建主窗口内的 `tk.Canvas`，首次显示与后续重排共用 `_layout_speech_bubble`，按原文重新测量与绘制；重排保留外层 Canvas 实例和自动关闭定时器。使用 Windows 窗口区域裁剪主体与尾巴之外的矩形背景，四角及尾巴两侧显示下方真实控件，无需透明色键或独立弹窗。
  - **绘制圆角与尾巴**：圆角主体采样为物理像素轮廓，Canvas 绘制与窗口裁剪共用同一组点（填充色 `#FFF7D8`，无边框、不再额外平滑）。在主体上方绘制指向蜗牛中心的三角形尾巴（宽度约16px，高约12px），颜色与主体一致；裁剪保留两者并集，重排同步更新区域。裁剪失败时关闭本次气泡并恢复相应暂停状态，不影响记账。
  - **文字**：使用 `canvas.create_text` 绘制文字，字体为 `("Microsoft YaHei UI", 11)`，颜色 `#3E4A5A`，居中显示。正文超出可用高度时，使用气泡内的 Canvas 视口与竖向滚动条保留全部文字，支持鼠标滚轮；不得靠截断文字或缩小字号避开高度限制。
  - **尺寸自适应**：气泡大小必须根据文字实际长度动态计算，不要固定宽高，不要留大片空白。
    - 显式换行、首尾与连续空行都保留；每个段落独立按像素宽度折行。测宽、算高与绘制共用最终可见行列表，正文上下各保留12像素、左右各保留18像素的内边距。
  - **精准定位**：使用与蜗牛定位一致的窗口内物理坐标及当前实际控件尺寸；通常在蜗牛正下方10像素处显示，正文连同尾巴限制在窗口12像素边距内。尾巴优先指向蜗牛中心，贴边时收进主体圆角之间，三角形不能越出 Canvas。
  - **缩放重排**：窗口、标题和蜗牛尺寸事件合并到空闲布局阶段，实际几何变化后才重排；单纯拖动主窗口不重排或续期。暂停时若蜗牛越界或压到新标题范围，将其收拢到最近的合法路线落点；长文重排尽量保留相对滚动进度。
  - **暂停移动**：点击蜗牛时，必须设置 `self.snail_paused = True` 暂停爬行动画（在 `_animate_snail` 里加判断拦截，但保持 `after` 循环不中断）。气泡消失后设为 `False`。
  - **自动消失**：泡泡显示3秒后自动销毁；长文每次主动滚动后重新计时3秒，尺寸重排不续期。如果用户连续点击，先取消旧定时器、销毁旧泡泡，再创建新泡泡并重新计时。
  - **点击销毁**：在气泡背景或正文按下鼠标后，松开时销毁气泡，并按焦点状态恢复蜗牛移动；由气泡接收完整点击，避免松开事件误触下方控件，按下后拖出气泡再松开同样关闭。滚动条操作只滚动正文；窗口区域裁剪掉的四角及尾巴两侧仍按原有行为穿透。
  - **消息读取**：继续读取 `snail_messages.json` 并随机抽取，如果出错显示默认提示语，不能崩溃。

### 3.8 应用图标 (Application Icon)
- 必须使用 `image/app_icon.ico` 作为整个应用的图标（窗口左上角、任务栏和自定义保存路径）（柱状图没改）。
- 在 `main()` 函数初始化 `AccountKeeperApp` 之后，调用 `iconbitmap` 加载该图标。
- **Windows 任务栏兼容**：为了防止任务栏把图标显示成 Python 默认图标，必须在设置图标前调用 `ctypes.windll.shell32.SetCurrentProcessExplicitAppUserModelID("AccountKeeper.App")`。
- **容错机制**：如果 `app_icon.ico` 文件丢失或格式损坏，程序不能崩溃，只需在控制台打印警告，并继续以默认图标运行。

### 3.9 搜索与筛选 (Search & Filter)
- **界面要求**：在顶部工具栏（按钮行）增加一个搜索输入框（`CTkEntry`），宽度约 200 像素。
- **【UI占位符】**：搜索框必须使用 `CustomTkinter` 的**原生占位符**参数 `placeholder_text="🔍 搜索日期/标签/备注"`。
  - 原生占位符的行为：平时显示灰色提示文字，鼠标点进去自动消失，用户可以直接打字；输入内容被清空后，提示文字自动回来。
- **实时过滤逻辑**：
  - 绑定 `self.search_var.trace_add("write", self.filter_records)`，用户每敲一个字符，就实时刷新表格。
  - 过滤规则：只要记录的**日期、备注或任一标签**包含搜索关键词，就显示该记录；每个标签独立匹配，不拼接标签后再搜索。
  - 搜索关键词不区分大小写（统一转小写比较）。
- **联动汇总**：汇总标签已删除，筛选只影响表格内容，不再需要同步汇总文案。
- **清空恢复**：当搜索框被清空时，立刻恢复显示所有记录。
- **工具栏自适应**：搜索框右侧的 6 个工具按钮（刷新 / 删除选中记录 / 月度统计 / 导出为CSV / 查看图表 / 打开数据目录）按可用空间等比例分配宽度，窗口缩放时同步调整；搜索框固定 200px，按钮之间保持 8px 间距；任何窗口宽度下按钮都完整可见、文字不被截断。
- **容错**：搜索时不能修改数据库，也不能报错，纯前端过滤。

### 3.10 图表可视化 (Chart Visualization)
- **依赖**：`matplotlib`。
- **触发方式**：在工具栏增加一个【查看图表】按钮。
- **弹窗逻辑**：
  - 点击按钮后，弹出月历让用户点选月份（返回值恒为严格的 `YYYY-MM`），复用现有的 `ask_month` 方法。
  - 如果该月无记录，弹出提示“该月没有记录”，不显示图表。
- **图表内容**：
  - 展示该月各标签的收入与支出总额；多标签记录分别计入每个标签，0 标签记录计入 `未分类`。
  - 使用**柱状图**（`bar`）展示：X 轴为标签，Y 轴为金额，收入向上、支出向下。
  - 图内必须显示说明：「一条记录有多个标签时会分别计入各项，故各项之和可能大于当期总额；未分类表示没有打标签的记录。」

  - 如果数据只包含收入或只包含支出，柱状图也应当能正常画出，不能因为某一项为0就拦截弹窗。
  - 如果该月没有任何记录（无论收支），才弹窗提示“该月没有记录，无法生成图表”，不显示图表。
  - 图表需支持中文显示（字体设为 `Microsoft YaHei`），标题为 `${月份} 收入与支出统计`。
- **新窗口展示**：
  - 图表必须显示在一个**独立的 `tk.Toplevel` 窗口**中，不能阻塞主界面。
  - 使用 `FigureCanvasTkAgg` 将 matplotlib 图表嵌入到 Tkinter 窗口中（不要用 `plt.show()`，否则会弹出独立的 matplotlib 窗口，风格不统一）。
  - 窗口大小约 700x550，居中显示在屏幕上。
- **容错机制**：
  - 关闭图表窗口时，释放 canvas 资源，避免内存泄漏。
  - 如果某些分类的名称过长，要确保图表上的标签不重叠（可以适当旋转X轴标签）。

### 3.11 记住上次导出路径（last_export_dir）

#### 目标
- **记住用户上次导出 CSV 时选的目录**，下次导出时作为「另存为」对话框的起始目录，省去重复点选。
- 不提供「自定义导出目录」入口：数据库固定为 `DATA_DIR / "account.db"`。

#### 配置文件
- 复用 `settings.json`，默认位置为**用户数据目录**（即 `DATA_DIR`，与 `account.db` 同目录）。
  - **说明**：不能放在项目目录（`BASE_DIR`）下。因为程序打包成 exe 后，项目目录通常是只读的，无法写入配置。
- 使用 UTF-8 写入，ensure_ascii=False, indent=2。
- 该文件只读写 `last_export_dir` 一个字段；不读取、不写入任何数据库路径字段。
- 容错规则：文件不存在、JSON 解析失败、字段缺失、路径非法或目录已被删除/不可写时，一律回退 `DEFAULT_EXPORT_DIR`（即 `DATA_DIR`），**静默处理：不弹窗、不崩溃**。
- `settings` 模块自身只允许在控制台打印警告，不得引入任何 UI 依赖（不 import customtkinter）。

#### 读取与写入时机
- **启动**：`account_keeper.py` 的 `main()` 调用 `settings.get_last_export_dir()`，把拿到的目录交给 `AccountKeeperApp`（`last_export_dir` 参数）。启动过程**不弹任何提示框**。
- **导出时**：`ui.export_csv` 打开「另存为」对话框时传 `initialdir=str(self.last_export_dir)`（见 3.6）。
- **导出成功后**：把用户实际选择的目录写回 `settings.json` 的 `last_export_dir`，并同步更新内存中的 `self.last_export_dir`；写回失败只在控制台警告。
- **用户取消「另存为」**：不写配置。

#### 模块接口（settings.py）
- `load_settings() -> (Path, bool)`：读配置；文件缺失/损坏/字段非法一律返回 `(DEFAULT_EXPORT_DIR, False)`，不抛异常。
- `save_settings(last_export_dir: Path) -> bool`：规范化路径（expanduser + resolve）并确认目录可写后写入；失败返回 `False`，不抛异常。
- `get_last_export_dir() -> (Path, bool)`：返回 `(可直接用作 initialdir 的目录, 是否用上了记住的目录)`；记录不存在或当前不可写时回退 `DEFAULT_EXPORT_DIR`。

#### 约束
- 不得修改 store.py 中 SQL 增删改查、事务的核心业务逻辑；数据库路径固定为 `DATA_DIR / "account.db"`，不接受配置覆盖。
- 路径记录只影响「另存为」对话框的起始目录，不涉及数据库位置。
- 所有路径选择、保存、校验逻辑必须放在 UI / settings 模块中，不能在 store.py 里写界面代码。

### 3.12 日历选择器 (Date Picker / Month Picker)

#### 目标
- 为日期字段与**月份**字段（统计 / 导出 / 图表）提供可视化的日历 / 月历选择，降低手动输入 `YYYY-MM-DD` / `YYYY-MM` 时的格式错误率。

#### 实现方式
- 新建 `calendar_picker.py`，对外提供两个函数。两者共用同一个弹窗实例与同一套「外壳」（顶部 ◀ / 标题 / ▶、底部左键 / 取消），差别只有两处：中段主体画什么（日期网格 / 月份网格）、◀ / ▶ 翻的是月还是年。
  - `ask_date(parent, initial_date: str, anchor: tk.Misc | None = None) -> str | None`
    - 返回值：选中日期的字符串（格式 `YYYY-MM-DD`），或 `None`（用户取消 / 按 ESC）。
    - `anchor`：日历弹出位置的锚点控件（日期输入框）。弹窗左边缘与它左边缘对齐、
      上边缘贴在它下边缘再往下 6 物理像素，下方放不下时翻到它上方；不传或已销毁时
      回落为屏幕居中。
  - `ask_month(parent, initial_month: str | None = None, anchor: tk.Misc | None = None, title: str = "选择月份") -> str | None`
    - 返回值：选中月份的字符串（格式 `YYYY-MM`），或 `None`（用户取消 / 按 ESC）。
    - `anchor`：含义与 `ask_date` 相同；统计 / 导出 / 图表三处调用点目前都不传，故走「屏幕居中」回退（原因见下方约束）。
    - `title`：弹窗标题，三个调用点分别传「选择统计月份」「导出账单」「查看图表」。
    - `initial_month`：命中的那格高亮显示、不直接选中；为 `None` 或解析失败时取 `date.today()` 所在月。
- 弹窗内容（日期模式，`ask_date`）：
  - 当前年月标题（如 `2026 年 9 月`）。
  - 上一月 / 下一月按钮（◀ / ▶）。
  - 星期表头（日 一 二 三 四 五 六）。
  - 7 列日期网格。
- 弹窗内容（月份模式，`ask_month`）：
  - 标题只显示当前**年**（如 `2026 年`）——月份模式的选中项是「哪一年的哪个月」，只显示「9 月」会分不清年份。
  - ◀ / ▶ 由「翻月」改为「翻年」（一次一年）。
  - 4 列 × 3 行共 12 个「n 月」格子（横向 4 列、纵向 3 行，列宽用 uniform 拉平）。
  - 底部左键由「今日」改为「本月」（跳回今天所在年并高亮本月，不关闭弹窗，仍需点一格确认）。
  - 弹窗比日期模式矮：逻辑 320 × 300（日期模式为 320 × 380）。
- 交互行为：
  - 高亮显示 `initial_date` / `initial_month` 命中的那一格而不直接选中；月份模式的高亮按 `YYYY-MM` 整串比对，翻年之后上一年的选中格会自动取消高亮。
  - 点击某日则返回该日（`YYYY-MM-DD`）；点击某月格则返回该月（`YYYY-MM`）。
  - 按 `ESC` 或点击「取消」返回 `None`。

#### 联动调用
- `widgets.py` 的 `InputFrame` 日期字段与 `dialogs.py` 的编辑弹窗日期字段都加上 ▼ 按钮，点击后调用 `ask_date`。
- 月份模式由三个工具按钮触发，都调用 `ask_month`：`ui.show_stats`（月度统计）、`ui.export_csv`（导出为CSV）、`chart_window._render_chart_window`（查看图表）。

#### 约束
- 日历弹窗使用 `CTkToplevel`，样式与现有弹窗保持一致（背景色 `#F0F4F8`、圆角按钮、`Microsoft YaHei UI` 字体）。
- 日期/月网格随外窗复用（最多42个日期格、固定12个月份格），翻页与重复打开仅更新变化内容及当前选择命令；空日期格隐藏且禁用，缩放后也不得重新出现。取消/选择仍清理会话、释放grab并隐藏外窗，真正销毁时清空控件缓存并唤醒等待，之后允许重新创建。
- 日期/月历打开时先隐藏更新本次内容，再透明映射取得真实尺寸；当前有效格子的画布完成映射、布局与位置稳定后一次显现并取得模态grab，避免展示旧模式或定位调整过程。准备期间取消/父窗退出须取消显现任务并唤醒等待，旧会话任务不得再次显示窗口；显现后仍允许拖动窗口。
- 主窗首次映射并完成一轮空闲布局后，在主线程隐藏预创建共用外窗及日期/月控件；格子按小批次准备当前月外观，每批让出事件循环，不显示窗口或取得grab。提前点击须取消剩余批次、复用已有控件并补齐本次内容/命令，退出须取消启动与预创建任务并唤醒模态等待；外壳构造不可分批，首次映射/绘制仍允许存在开销。
- 月份选择器已随 #3.2 实现（上面三处调用点由「弹输入框手输 `YYYY-MM`」改为「点月历选月份」）。原先由 `dialogs.ask_month` 的 `re.fullmatch` 兜住的「`month` 恒为严格 `YYYY-MM`」这一安全性前提，现在由 `calendar_picker.ask_month` 保证：返回值只可能来自 4 × 3 月历的格子，项目里不再有手输 `YYYY-MM` 的入口。
- （现状）上面三处调用点都不传 `anchor`，因此月份弹窗固定在**屏幕居中**显示，而不是像日期 / 类别弹窗那样贴住唤起它的按钮——工具栏 6 个按钮在 `widgets.ToolbarFrame` 里就地创建、没有留下控件引用，调用点拿不到锚点。补齐需要 `widgets.py` 暴露按钮引用 + 3 个调用点透传 `anchor`，见 issues.txt #60（待目视确认居中效果后再决定是否做）。

### 3.13 类别选择器 (Category Picker)

#### 目标
- 降低类别输入成本，同时避免同一类开销出现多种写法（比如「餐饮」「吃饭」「午饭」各存一份），让 3.4 统计和 3.10 图表里的类别维度真正能聚合到一起。

#### 实现方式
- 类别字段改用「**输入框 + ▼ 按钮**」的组合（新增记录输入区与编辑弹窗都改），风格与日期字段的 ▼ 按钮完全一致（36px、圆角 9px、`#E3EAF2`，hover `#D2DEE9`）：输入框始终可编辑，因此**仍然可以直接手输新类别**；点 ▼ 按钮弹出类别选择列表。
- 弹窗由 `tag_picker.py` 提供，入口是 `ask_tags(parent, anchor, current="", toggle_button=None, *, selected_tags=()) -> tuple[str, ...] | None`：`selected_tags` 是每次打开时从调用方当前 chips 传入的快照；点候选只切换选中态，点「完成」整体回填元组，其他关闭路径返回 `None`。候选由弹窗从 `tag_prefs.build_tag_candidates()` 现算，不由调用方传入，也没有方向参数。`toggle_button` 用于识别再次点击 ▼ 并同步 ▲ / ▼ 图标。
- 弹窗宽度与位置按锚点（类别输入框）实时对齐，打开期间锚点或窗口移动/缩放会跟着走。
- 窗口与固定布局跨次复用；候选每次现读，按去重后的标签名保留行控件，新增才创建、移除才销毁、排序与选中变化按需更新，保存/置顶/删除共用同步出口。首次出现50项仍需创建50行，本版不做虚拟化。
- 每次打开重建独立会话，复位选择/结果/输入/提示/滚动/锚点，隐藏同步后再显现；关闭清理本次任务/绑定、归还按钮文字及合法原grab、隐藏并通知等待信号。缓存仍属首次真实父窗，创建父窗销毁或closing时作废，下次重建；当前调用父窗退出同样结束会话，保留构建期延期关闭保护。
- 候选列表 = **`tags.json` 中唯一的 `tags` 列表**（由 `tag_prefs.build_tag_candidates() -> list[str]` 现算）。列表里有什么就显示什么：保存后出现、删除后消失；支出与收入共用同一列表。
  - `config.DEFAULT_TAGS` 共 17 项：支出 10 项按原序在前，收入中未出现的 7 项按原序追加；重复的「其他」只保留一次。
  - 初始化时优先迁移旧 `categories.json`；仅在旧文件不存在或损坏 / 格式非法时，才把 `DEFAULT_TAGS` 与数据库历史标签按顺序去重后写入。

#### 弹窗底部操作区（footer）
- footer 分两块：**第一行**是「新类别输入框 + 「+ 保存」按钮」，输入框占满「弹窗宽度 − 保存按钮 − 内边距」、按钮钉在右端（与日期/类别字段「输入框 + 图标按钮」是同一套左右分栏写法）；**第二行**是一行提示语「输入新类别后点 + 保存」，占满整行宽度。提示语明说「要在这里输入」，以免用户以为在主窗口那个框里打的字已经被收下了；它同时承担「写盘失败时报错」的职责，所以不能省（`messagebox` 不能用，见下）。「×」与「顶」不另做图例：前者是通用符号，后者本身就是汉字、语义自明；弹窗最窄时一行里也塞不下第二句说明。
- **footer 自带输入框**：
  - 这是弹窗**自己的**输入框，**不绑主窗口的输入变量**，也不做双向同步；`tag_prefs` 的写入完全以它里面的文字为准。
  - 打开弹窗时**预填主窗口输入框此刻的内容**（即 `ask_tags(..., current=...)` 传进来的值）。预填只在建窗时读一次。
  - 之所以把输入框搬进弹窗，是因为原设计（「+ 保存」去读主窗口输入框的内容）要求用户「先在主窗口打字 → 再点 ▼ → 再点保存」，实际用起来很绕；输了搬进来之后「打字 → 点保存」两步就够了。
  - 输入框**不设占位符（placeholder）**：占位符的语义是「里面没字时才显示」，与「预填 `current`」互斥（CustomTkinter 的占位符在失焦且为空时还会自己回来，和预填内容打架）。它的用途改由下面那行提示语说明。
  - 输入框里按**回车**等价于点「+ 保存」，符合「打字→提交」类输入框的通用习惯。
- **「+ 保存」**：把 **footer 输入框**里此刻的内容存进 `tags.json` 的 `tags` 列表（`tag_prefs.save_tag`）。
  - 输入框为空时提示用户先输入，不写盘。
  - **成功后清空输入框**：拿「框空了」当一次「已经收下了」的反馈。标签原本就在列表里时 `save_tag` 同样不报错、列表看不出任何变化，不清空的话用户分不清刚才那一下到底生效没有，只会忍不住再点一次。
  - **失败时保留输入框内容**：用户多半想照着这个名字重试，或者去手工检查文件，清空等于逼他重新打一遍。提示语变成警示色并说明原因。
  - **成功后列表滚到底**：`save_tag` 的语义是**追加到末尾**，而列表超过 7 项时视口装不下，不滚的话新项就落在折叠线以下、用户看不到自己刚存的那一项。
- **保存成功、置顶成功都不弹任何提示**：列表里当场多出一项 / 某一项跑到最前面就是最直接的反馈，再弹一句「保存成功」反而要多点一次才能继续。
- **列表项右侧的「顶」按钮（置顶）**：点它把该标签移到列表最前（`tag_prefs.move_tag_to_top`），列表重画后它出现在第一行。
  - **位置在「×」左边**：`×` 保持「整行最右那个按钮 = 删除」的位置不变。误点代价不对称——置顶是可逆的一下点击，删除不可逆，把「顶」插到最右会制造「想删除却点了置顶」的误操作，而反方向的误操作只是多点一次。
  - **第一行的「顶」置灰禁用**：它已经在最上面了，再点没有任何作用。刻意「置灰」而不是「这一行不画这个按钮」——不画会让第一行的名字按钮变宽，鼠标从第二行往上移时点击落点会跳；置灰则每一行的宽度完全一致。禁用色显式指定浅灰，不用主题默认值（主题默认的 `gray74` 比正常态还深，看起来反而更醒目，与「不可点」刚好相反）。
  - **不给文字反馈**：列表本身的变化（目标项移到最前）就是反馈，再写一句「已置顶」是多余的；只有写盘失败才用提示语报错。
  - **置顶后列表回到顶部**：该项刚跑到最上面，而列表超过 7 项时视口装不下——不滚上去的话用户只看到它从原来的位置消失、看不到它去了哪，会误以为是删除。
  - **置顶不改变行数与弹窗高度**：它只是列表内重排，`_render_list()` 之后行数不变，因此高度公式与「高度只在行数变化时改」这条规则都不受影响。
- **列表项右侧的「×」按钮（真删除）**：点它把该标签从列表里删掉（`tag_prefs.delete_tag`），列表当场重画、该项消失，下次不会再出现。想找回来只能重新用「+ 保存」输入同名标签。
  - **没有二次确认**：`messagebox` 在弹窗里不能用（它是另一个顶层窗口，会被「点弹窗外就关闭」的监视器当成外部点击，反而先把列表关掉），而且需求要的就是「删掉就是真的没了」这条直白语义。
  - **不区分预置项与用户自建项**：预置项在首次启动时就已经写进 user 变成普通列表项了，删除走同一条路，不需要特殊分支。
- **「+ 保存」「顶」「×」这三个动作都不关闭弹窗**：保存完通常紧接着就要点刚出现的那一项，删完可能想接着删下一个，置顶更是「换一下位置」这种轻量意图，关掉再让用户点一次 ▼ 是多余的往返。
- 符号选型：用 `×`（U+00D7），它是 `Microsoft YaHei UI` **自带**字形、不依赖 Windows 字体回退，也是各 App 里「删除这一项」的通用符号；刻意不用 `✕`(U+2715)——它在该字体里没有字形，靠字体回退才显示得出来，跨环境一致性差一些。置顶用汉字 `顶`（U+9876），同样在该字体里自带字形（实测 glyph `0x0bbd`，不靠回退）；备选的 `↑`(U+2191) 虽然有字形，但箭头很容易被读成「上移一位」这个相邻操作，而「顶」单字宽 20 逻辑像素（字号 12）、28px 的按钮装得下，语义也更直白。写成两个字「置顶」实测需要 40px，按钮得加宽到 44px、会挤掉类别名的位置，所以只用单字。
- 写盘失败的提示**不用 `messagebox`**：`messagebox` 是另一个顶层窗口，弹出时正好落在「点击弹窗外就关闭」的监视范围内，会把刚开的列表直接关掉，反而掩盖了真正要说的信息；统一复用 footer 的提示语块。

#### 交互行为
- 切换【支出 / 收入】时，候选列表**不变**：两种方向共用 `tag_prefs.build_tag_candidates()` 返回的单一列表。
- 用户手输的新类别**不会**自动进入候选：想让它进列表，要在弹窗底部的输入框里确认/输入后点「+ 保存」。这是刻意的——手输常常只是一次性的写法（「午饭」「吃饭」），只有用户明确点「保存」才代表「以后还要用」，候选列表因此不会被一次性输入污染。保存成功后列表当场多出该项，可直接点选。
- **弹窗输入框与主窗口输入框互不写回**：主窗口那个框的内容只会在打开弹窗时单向**预填**进弹窗（见「弹窗底部操作区」），反过来不成立。因此「在弹窗里改了但没点 + 保存就关掉」不会改动主窗口（走 5 种关闭方式中的任意一种都一样）；弹窗输入框的内容也**不参与**「点选某项回填输入框」这条唯一的回流路径。
- 切换【支出 / 收入】时**不清空已输入内容**：已填好的类别不会因为改了收支类型而丢失。
- **关闭方式（共 5 种）**：① 再点同一个 ▼（toggle）② 点「完成」确认整组选择 ③ 按 `ESC` ④ 点右上角 × ⑤ 点击弹窗外。其中**只有 ② 返回有序标签元组**，其余 4 种取消临时选择，一律返回 `None`；点候选只切换选中态、不关窗。弹窗被父窗口连带销毁时同样不修改调用方标签。
- **图标跟随开合**：弹窗打开期间，唤起它的那个 ▼ 按钮文字翻成 ▲；弹窗关闭时（无论走上面 5 条中的哪一条，还是被父窗口连带销毁）都由 `tag_picker._end_session()` 统一翻回 ▼——集中在一处是为了不漏路径。
- **弹窗高度** = 上下内边距 + 列表视口高度（最多露出 7 项，超出靠滚动条）+ 列表区圆角增量（列表控件上下各留一个圆角半径，共 2 × 8px = **16px**，算漏了最后一行就得滚动）+ 列表与 footer 之间的缝隙 + footer 高度（28px 输入框/按钮行 + 4px 行距 + 18px 单行提示语 = **50px**）。列表视口高度按**实际候选数**算（保存多一项 / 删掉一项都会当场改高度），但封顶 7 项；调高度时宽度保持不变（宽度由定位逻辑按锚点实时决定）。
- **再点 ▼ 关闭（toggle）**：弹窗已打开时再次点击同一个 ▼ 按钮，视为关闭——只关闭列表，**不修改输入框内容**，也不会因这次点击而填入任何类别。
- **点击弹窗外关闭**：点击弹窗以外的任意界面区域即关闭列表，同样**不修改输入框内容**；此时若用户已选好类别，关闭动作不会影响已有输入。
- **ESC 关闭**：焦点在弹窗内时按 `ESC` 关闭，效果等同于「不做选择地关掉列表」。
- **不叠加**：打开新弹窗时若已有类别弹窗存在，先关闭旧的再打开新的，避免连点 ▼ 造成多个弹窗互相叠加。
- **刻意不 grab**：类别弹窗**不使用** `grab_set()`（与 `calendar_picker.py` 的做法相反），因为 grab 会吞掉弹窗外的一切鼠标事件、导致第二次点 ▼ 进不来。代价是弹窗不再模态——**关掉它的那一次外部点击会同时作用到被点的控件上**（例如点在「添加」上就会真的添加一条记录）。这两点无法两全，本版本选择 toggle 行为。
- 编辑弹窗打开期间若弹出类别列表，类别弹窗会**临时借用**编辑弹窗的 grab，关闭时原样归还，以保证编辑弹窗的模态性在类别列表关闭后立即恢复。

#### 标签数据模型（tag_prefs）
- 新标签偏好写入 `tags.json`（`config.TAG_PREFS_PATH`），结构为 `{"version": 1, "tags": [...]}`；旧 `categories.json`（`config.CATEGORY_PREFS_PATH`）只作为迁移输入，保留原文件不改不删。
- 标签偏好存在用户数据目录的 `tags.json`（`config.TAG_PREFS_PATH`），结构如下（**单一列表、无收支方向**，Q1）：
  ```json
  {"version": 1,
   "tags": ["餐饮", "家庭", "报销"]}
  ```
- `version`：写为 1；读取时按 `tags` 列表结构取值，无法解析或结构不合法时按空状态处理，后续写操作可恢复标准格式。
- 标签池只有一份 `tags` 列表、不分收支方向。首次初始化按三路判定：`tags.json` 已存在则完全不动；否则旧 `categories.json` 存在且结构有效时，先并入 expense 全段，再按原序追加 income 中未出现的项，不追加数据库历史；旧文件损坏 / 格式非法时按旧文件不存在处理，使用 `DEFAULT_TAGS + history`；两份文件都不存在时同样使用 `DEFAULT_TAGS + history`。后两路按首次出现顺序去重。旧文件始终只读并保留。
- 标签列表是唯一真源；保存、真删除与置顶接口分别为 `save_tag(name)`、`delete_tag(name)`、`move_tag_to_top(name)`，均返回布尔值。删除不存在的标签、置顶不存在或已在首位的标签均幂等成功且不重写文件。
- `build_tag_candidates() -> list[str]` 每次现读文件，不缓存；切换支出 / 收入不会改变候选。
- `ensure_tags_initialized(history) -> bool` 负责上述三路初始化；历史由 UI 作为参数传入，偏好模块不导入 store。`tags.json` 已存在时不改写；写入失败不阻断启动。损坏的 `tags.json` 后续可由 save / delete / pin 写接口覆盖恢复。
- 为什么另立 `tags.json` 而不并进 `settings.json`：`settings.save_settings` 是**整份覆盖**写入，标签数据同住一个文件会被下次导出路径写回时整段抹掉；且 settings 的契约是「任何异常静默回退」，而标签是用户显式保存过的主动意图，静默丢弃等于数据损失，两者容错等级不同。

#### 历史标签来源（仅用于首次启动初始化）
- `store.get_tags() -> list[str]`：从 `record_tags` 返回去重、按字典序排列的历史标签。
- UI 启动时把该列表传入 `tag_prefs.ensure_tags_initialized(history)`；有效旧偏好文件优先于数据库历史。

### 3.14 多标签改造

> **本节是「标签替代类别」改造的唯一权威规格**：本节与上文任何描述冲突时，**以本节为准**。改造方向是把现有的「类别」字段整体**替换**为「多标签」——不是新增一个维度，而是把「一个桶」扩成「多个桶」。

#### 3.14.1 语义与定位
- **一条记录可打 0..N 个标签**（Q2 允许 0 个）。0 个标签是合法的「快速记一笔」，不强制分类。
- **标签 = 自由输入 + 常用列表混合**：手输的标签立刻生效、只属于这一条记录；想让它以后能从列表里直接选，需显式保存进常用列表（沿用 §3.13 的「+ 保存」交互与语义）。
- **老记录的 `category` → 单标签**：一对一迁移，**不猜、不拆词**（`餐饮/外卖` 不会自动拆成两个标签——没有依据能判断用户当时想不想拆）。
- **标签无收支方向**（Q1）：支出与收入共用同一个标签池，`tags.json` 只有一份列表。
- **为什么是「替代」而不是「并存」**：并存意味着用户要维护两份元数据（类别列表 + 标签列表）、输入区多一行、图表多一个维度切换、统计口径翻倍；而用户诉求的本质只是「一笔钱同时属于几个桶」——「类别」本来就是「一个桶」的单值版本，把它扩成多值即可，不需要再留一套旧维度。并存还会造出「类别是主、标签是辅」的隐性层级，而这个层级在产品上没有任何需求依据。
- **必须承认的语义损失**：多标签下「一条记录的标签之和」不再等于「当期总额」，因为一条记录会被计入多个标签。§3.14.4 用「分别计入 + 诚实标注」处理这一点，而不是把它藏起来。

#### 3.14.2 数据结构与迁移

**推荐 schema：`record_tags` 关联表（方案 A′）——不建标签字典表**

```sql
CREATE TABLE IF NOT EXISTS record_tags (
    record_id INTEGER NOT NULL,
    tag       TEXT    NOT NULL,
    PRIMARY KEY (record_id, tag)          -- 复合主键天然去重：同一条记录打两次同名标签只留一行
);
CREATE INDEX IF NOT EXISTS idx_record_tags_tag ON record_tags(tag);   -- 支持按标签聚合 / 筛选
```

职责切分（本方案的关键，也是与被否方案的分歧点）：
- **数据库记「哪条记录用过哪些标签」**（`record_tags`，多对多，带引用完整性，可被 SQL 直接筛选 / 聚合）；
- **`tags.json` 记「用户想常驻列表的标签」**（常用列表，唯一真源，`build_tag_candidates()` 只读它）。

被否方案与理由：

| 方案 | 做法 | 否决理由 |
|---|---|---|
| A：三表 | 另建 `tags(id, name)` 字典表，`record_tags` 存标签 id | 多一张表就多一次 upsert、多一处改名要同步；而「候选列表的唯一真源是 json 文件」这一点已在 issues #48 / #53 两轮反复确立，数据库再存一份标签名 = **两处真源**，正是前两轮一直在消掉的那类问题 |
| B：`accounts.tags` 存 JSON / TEXT | 在 `accounts` 表加一列，值形如 `["日用","家庭"]` | 改动最小，但 ① SQL 无法按标签筛选 / 聚合（只能全表捞出来在 Python 里解析）；② JSON 没有形状约束，脏数据能悄悄写进去；③ 把关系藏进字符串，将来想加「标签使用次数」「按标签 TopN」还得先解析。**仅在工期极紧时作为降级备选** |

**`accounts.category` 列怎么处理：保留、停止写入、降为 legacy 只读**
- 改造后 `add` / `update` **不再写 `category` 列**；标签只写进 `record_tags`。
- **不删列**，三条理由：① 迁移后随时能 `SELECT id, category FROM accounts` 与 `record_tags` 对账，出问题能反查；② `ALTER TABLE ... DROP COLUMN` 不可逆，且用户手上若有旧版 exe，新库少一列会让旧版直接报错崩溃；③ 留着的成本是 0（只是多一列旧数据）。
- `Account.category: str` → `Account.tags: tuple[str, ...]`（用 tuple 而非 list：不可变，能防调用方原地改缓存、也能当 dict key）。
- **迁移过程不改 `accounts` 表的任何内容**，只往 `record_tags` 里写 → 整个迁移可回滚。

**迁移策略（`PRAGMA user_version`，目标版本 2）**
1. **版本标记用 SQLite 自带的 `PRAGMA user_version`**（初始 0，迁移后置 2）。选它而不是自建标记表 / 在 `settings.json` 里加字段：① SQLite 自带、无需额外文件；② 一条 `PRAGMA user_version` 就能从命令行或探针直接看出库处于哪个版本；③ 以后再加迁移就继续 2 → 3，不必每次发明新标记。
2. **仅存在待补标签记录时备份**：先数出「`category` 去除首尾空白后非空、且在 `record_tags` 里一行关联都没有」的记录数；为 0 时既不备份也不改数据，只把版本号抬到目标值（没有退路可言，就不该在用户目录里留下一个空的 `.bak`）。有待补记录时把 `account.db` 复制为同目录的 `account.db.bak`；备份失败则**中止迁移**（不写标签、不升版本，下次启动重试）并只打控制台警告（不崩窗口）——宁可这次不迁，也不能在没有退路的情况下改库。
3. **迁移动作（幂等）**：只给没有标签关联的记录补标签，避免给已有标签的记录重复补入旧 `category` 值；空 / 纯空白的 `category` 不产生标签（正好对应 Q2「允许 0 标签」）。
4. **低于目标版本 2 时才跑，一次到 2**：`0 → 1` 与 `1 → 2` 做的是同一件事——给零标签记录补一行关联，因此两段复用同一段幂等逻辑；仅当 `user_version < 2` 时执行，补标签与升版本在同一事务里提交，不会出现「标签写了、版本却没升」的半迁移状态。迁移**只读 `accounts` 的 `category` 列**，不动 `note` / `amount` / `record_date`。

**Q1 的标签池合并迁移（`categories.json` 两段 → `tags.json` 一份）**
- 旧结构：`{"version": 1, "expense": [...], "income": [...]}`；新结构：`{"version": 1, "tags": [...]}`（**单一列表，无方向**）。
- **三路初始化**：`tags.json` 已存在 → 不读其它来源、不改文件；`tags.json` 不存在且 `categories.json` 有效 → 合并旧两段并写新文件；`tags.json` 不存在且旧文件缺失、损坏或格式非法 → 写 `DEFAULT_TAGS + history`。
- **旧文件合并顺序**：结果 = `expense` 全部（按原序）+ `income` 中未出现过的项（按原序），去重、不排序；此路不追加数据库历史。坏 / 非法旧文件按不存在处理，走预置 + 历史路，不能把升级用户的候选清空。
- **两份文件与历史**：`categories.json` 只读、保留原样不删除；`tags.json` 存在时完全不动；只有旧文件不可用或不存在时才使用数据库历史标签。
- **用户已用过的标签一个都不能丢**：合并是取「并集」而非「取其一」，两段里的每一项都会出现在新列表里。

**与 issues #40 的区别（重要，避免后续实现时被这条挡住）**
- #40 删掉的是「**从另一种存储介质（旧版 CSV）导入数据**」，当时的判断依据是「本项目从未发布、不存在真实用户从旧版本升级」，所以那套迁移是纯负担。
- 本节是「**同一个库内部的结构升级**」：用户本地的 `account.db` 里就躺着他自己录进去的数据，不迁移 = 数据丢失。两者**性质完全不同**，不能拿 #40 当理由跳过本节迁移。

**老数据不丢的三重保证**
1. 迁移前 `account.db.bak` 备份（出问题可整库还原）；
2. 旧 `categories.json` 保留不删（常用标签列表可回滚）；
3. 迁移 SQL 全部用 `INSERT OR IGNORE`、且不改写 `accounts`（不覆盖 / 不破坏任何既有数据）。

**配套改动**：`.gitignore` 需加 `account.db.bak`——现有 `account.db` 规则**匹配不到**这个新文件名。

#### 3.14.3 UI 形态

**形态 1（目标形态）—— chips + 多选弹窗**
- §3.2 的输入区第二行由「类别字段（输入框 + ▼）」改为**标签区**：
  - 若干**标签 chip**（每个 chip 尾部带一个 `×`），末尾一个窄输入框 + `▼` 按钮；
  - 输入框里打字 + `回车` → 当场变成一个 chip；
  - 点 chip 上的 `×` → 删掉该 chip。**这次删除只影响本条记录，不动 `tags.json`**（与 §3.13「× 删的是常用列表里的项」是两件事，最容易混淆）；
  - 0 个标签时标签区只剩输入框（合法状态，见 Q2），不显示任何占位提示。
- `▼` 弹窗由单选取值改为**多选切换**：点一项切换它的选中态、**不关窗**（可连点多下）；关闭弹窗时把**选中集合整体回填**成 chips。其余关闭方式（toggle / ESC / 右上角 × / 点弹窗外）语义不变，仍然不回填。
- 选形态 1 的理由：用户一眼就能看到「这条打了 3 个标签」；形态 2 只显示一串文字、看不出个数、还得记住分隔符。
- **布局连带影响（必须一起改，不能只换控件）**：第二行不再是固定 36px 高的输入框，而是一个**高度可变区域**（chips 换行时高度会长），牵动三处：
  1. §3.2 的 **15 : 25 列权重网格**（标签区跨列 / 占满一行的方案要重新定）；
  2. `widgets.InputFrame` 与整张卡片的**高度**（不能再按固定两行高度算）；
  3. 弹窗（日历 / 标签选择器）按锚点定位的**锚点几何**（锚点高度可变，定位算式要跟着算）。

**形态 2（降级备选）—— 分隔符文本**
- 仍是单行输入框，多个标签用 `,` 分隔（如 `日用, 家庭`）；`▼` 弹窗多选，但回填成一整串文本。
- 优点：几乎不动布局（沿用现有 36px 输入框与 15:25 网格），改动最小。
- 缺点：界面上仍是一串文本，用户看不出「打了几个标签」，还得记住分隔符。
- **关键解耦说明**：schema（§3.14.2）、CSV / 图表口径（§3.14.4）与 UI 形态**完全无关**。工期紧时可**先落形态 2，不会造成返工**——后续换成形态 1 只需改 `widgets.py` / `dialogs.py` / `tag_picker.py` 三个文件的表现层。

#### 3.14.4 统计与导出口径

| 场景 | 口径 | 为什么这么定 |
|---|---|---|
| 表格单元格（§3.3） | 多个标签用**顿号**连接（`日用、家庭`）；0 标签显示 `—` | 表格是给人读的，顿号比逗号 / 竖线更像中文并列；超宽由 `ttk.Treeview` 自然截断 |
| CSV（§3.6） | 多个标签用 **`\|`** 连接（`日用\|家庭`）；0 标签写**空串**；`CSV_FIELDS` 的标签列名为 `tags` | 若用逗号，`csv.writer` 会给这个字段**自动加双引号**（`"日用,家庭"`）——虽然合法，但用户拿 Excel「文本分列」或用脚本 `split(',')` 处理时会踩坑；`\|` 在标签名里极罕见，整行仍是规整的逗号分隔 |
| 搜索（§3.9） | **任一标签命中即算命中**；占位符改 `🔍 搜索日期/标签/备注` | 与「日期 / 备注包含即命中」同一套 OR 语义。刻意不引入「必须全部标签命中」——那要求用户先想清楚当前是哪一套匹配模式，属于需要解释的隐藏状态 |
| 编辑弹窗校验（§3.5.1） | 允许 0 个标签（Q2） | Q2；「我就想快速记一笔」是常见诉求，强制分类是产品洁癖 |
| 月度统计（§3.4） | 列出各**标签**的支出明细，口径同图表；明细之和可能大于总支出时显示同口径说明 | 「分类」就是「标签」在改造前的名字；说明避免把分别计入误解为金额错误 |
| 图表（§3.10） | X 轴为**标签**；一条记录多标签则**分别计入每个标签**；并新增 **`未分类` 虚拟桶**；图内**必带**文字标注 | 见下面两条 |

**为什么图表要「分别计入」而不是「只算第一个标签」**
- 「只算第一个」等于给标签偷偷引入**主次关系**，但 UI 上根本没有「主标签」这个概念：用户把两个标签的打字顺序换一下，图表就变了——这是无法向用户解释的行为。
- 「分别计入」与搜索口径**自洽**：两个标签都能筛到这条记录，那么两个标签也都该在图表里统计到它。
- 代价必须**诚实标注**，不能藏起来：一条记录被计入 N 个标签，所以「各标签之和」可能**大于**当期总额。因此图表内必须带一行说明文字：「一条记录有多个标签时会分别计入各项，故各项之和可能大于当期总额；未分类表示没有打标签的记录。」

**`未分类` 虚拟桶：允许 0 标签（Q2）的必要配套，必须计入统计与图表**
- 因果链：Q2 允许 0 个标签 → 0 标签的记录**不属于任何标签** → 如果图表只按标签聚合，这些记录会在图上**彻底消失**（既不在任何一根柱子里，也不参与任何校验），用户会看到「这个月明明花了钱、图上却是空的」。
- 所以「分别计入」必须配一个出口：**0 标签的记录统一计入名为 `未分类` 的虚拟桶**。它只存在于统计 / 图表口径中——**不写进 `record_tags`、也不是 `tags.json` 里的标签**，用户不能手动打上它、也不能删掉它。
- 若省略此桶，零标签记录将不在统计与图表中出现，等于把 Q2 变成数据不可见的 bug。
- `未分类` 桶同样计入「分别计入」的总额口径，因此它也在那行诚实标注的覆盖范围内。

#### 3.14.6 决策的答案与理由

| # | 决策 | 理由 |
|---|---|---|
| Q1 | 标签池**合并成一个列表**（不分收支方向） | 「家庭」「旅行」「报销」等标签在收支两侧都合理；用户维护两份列表是折磨 |
| Q2 | **允许 0 个标签** | 「我就想快速记一笔」是常见诉求；强制分类是产品洁癖。（配套：§3.14.4 的 `未分类` 虚拟桶） |
| Q3 | 保持**真删除**，不恢复隐藏机制 | 删除已解决问题；恢复隐藏反而制造「我删了怎么还有」的困惑（与 issues #51→#53 的方向一致） |
| Q4 | UI 用**形态 1**（chips + 多选弹窗） | 用户一眼看到「打了 3 个标签」，最直观 |
